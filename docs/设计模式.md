# 设计模式

## 1.单例模式

核心思想是保证**一个类只有一个实例，并提供一个全局访问点来访问这个实例。**

这句话听起来有点抽象，我们把它拆成两半来理解：

- **只有一个实例**：在整个应用程序的运行过程中，这个类自始至终只存在一个对象，而不会被重复创建出好几个长得一样的对象。打个比方，一个公司只有一位 CEO，无论谁来找，找到的都是同一个人。

- **全局访问点**：既然只有一个实例，那别人怎么拿到它呢？这个类会对外提供一个统一的入口（通常是一个静态方法），不管在程序的哪个角落，都通过这个入口来获取那个唯一的实例。

  ### 为什么要使用单例设计模式呢

  简单来说，单例设计模式有以下几个优点，值得我们考虑使用它：

  - **全局控制**：既然全场只有一个实例，我们就能严格地管住「谁能用它、什么时候用它」，也就是对这个唯一实例的受控访问。
  - **节省资源**：正因为只有一个实例，就不必反复创建相同的对象，从而省下了系统资源；而且多个模块还能借助这个共同的实例来共享数据。
  - **懒加载**：单例模式可以实现懒加载，也就是用到的时候才创建，没用到就先不占地方，这无疑能提升程序的性能。

  ### 单例设计模式的基本要求

  想要实现一个单例设计模式，必须遵循以下三条规则：

  - **私有的构造函数**：把「造对象」这扇门锁起来，防止外部代码直接 new 出新的实例。
  - **私有的静态实例变量**：在类内部找一个固定的位置，专门保存这唯一的一份实例。
  - **公有的静态方法**：对外开一个窗口，别人想要实例时，都通过这个方法来领取。

  可以这样理解：构造函数私有是「不让你自己造」，静态实例变量是「我帮你提前备好那一份」，静态方法则是「想要就来我这儿拿」。三者配合，才能保证全场始终只有一个实例。

  ### 单例设计模式的实现

  单例模式的实现方式有多种，最常见的是「饿汉式」和「懒汉式」两种，从名字就能看出它们的性格差异。

  饿汉式指的是在**类加载时就已经完成了实例的创建**，不管后面这个实例有没有被用上，先创建出来再说——就像一个饿坏了的人，饭还没上桌就急着把碗端好了，所以叫做“饿汉”。

  而懒汉式则恰恰相反，只有在真正请求实例时才会去创建：第一次有人来要、发现还没创建，就现做一个；之后再有人来要，就直接把已有的那个递过去。一句话概括就是**用到了再创建**，能拖就拖，所以称为“懒汉”。

  这两种写法在单线程下都没问题，但一到多线程环境就有了区别。饿汉式在程序启动阶段就把实例准备好了，自然不存在多个线程抢着初始化的问题；而懒汉式不一样：如果多个线程同时访问 `getInstance()`，又恰好在同一时刻都发现「实例还没创建」，它们就可能各自创建出一个实例，结果一不小心造出了好几份，单例也就名存实亡了。

  **（懒汉式加载存在竞态问题）**

  > 举个例子，你和小明都发现家里没米了，在你们没有相互通知的情况下，都各自跑去超市买了一袋米，这样就重复购买了，正好违背了单例模式「全场只有一份」的初衷。

  要解决这个问题，我们可以引入一些同步机制，比如用互斥锁，确保在任何时刻都只有一个线程能执行创建实例的动作——就好比你和小明约定好「谁先到厨房谁来管买米」，避免重复采购。

  下面以 Java 代码为例，说明单例设计模式的几种基本写法：

  1. 饿汉模式：实例在类加载时就被创建。这种写法实现起来最简单，缺点是如果这个实例最终没被用上，就白白占用了资源。

  ```java
  public class Singleton {
  
      private static final Singleton instance = new Singleton();
  
      private Singleton() {
          // 私有构造方法，防止外部实例化
      }
  
      public static Singleton getInstance() {
          return instance;
      }
  }
  ```

  1. 懒汉模式：第一次使用时才创建。下面的写法用 `synchronized` 给整个方法加了锁，从而保证线程安全，代价是每次取实例都要等锁，会略微影响性能。

  ```java
  public class Singleton {
  
      private static Singleton instance;
  
      private Singleton() {
          // 私有构造方法，防止外部实例化
      }
  
      // 使用了同步关键字来确保线程安全, 可能会影响性能
      public static synchronized Singleton getInstance() {
          if (instance == null) {
              instance = new Singleton();
          }
          return instance;
      }
  }
  ```

  注意到上面那种写法每次取实例都要排队等锁，其实有点浪费——因为实例一旦创建好，后面就只是读取而已，根本不需要再加锁。于是在懒汉模式的基础上，我们可以使用「双重检查锁」来提高性能：先不加锁地看一眼实例是否已存在，只有在确实需要创建时才加锁，加锁后再确认一次，这样就把加锁的开销降到了最低。

  ```java
  public class Singleton {
  
      private static volatile Singleton instance;
  
      private Singleton() {
          // 私有构造方法，防止外部实例化
      }
  
      public static Singleton getInstance() {
          if (instance == null) {
              synchronized (Singleton.class) {
                  if (instance == null) {
                      instance = new Singleton();
                  }
              }
          }
          return instance;
      }
  }
  ```

  ### 什么时候使用单例设计模式

  说了这么多，那到底在什么场景下该考虑使用单例设计模式呢？我们可以对照着前面提到的几个优点来判断。

  1. 资源共享

  当多个模块需要共享同一份资源时，单例模式就派上用场了。比如应用程序需要一个全局的配置管理器来统一存放和读取配置信息，又或者用它来管理数据库连接池——让大家用的都是同一份，既省资源又不会乱。

  1. 只有一个实例

  当系统中某个类天生就只需要一个实例来统筹全局时，可以考虑用单例模式。比如管理应用程序的缓存，保证只有一个缓存实例，避免缓存被重复创建、各管各的；又或者用它来创建和管理线程池。

  1. 懒加载

  如果一个对象创建起来本身就比较消耗资源，而且在整个程序里还不一定用得上，那就很适合用单例模式实现懒加载——真正需要时再创建，不需要时绝不浪费。

  其实在许多流行的工具和库中，也都能看到单例设计模式的身影。比如 Java 中的 `Runtime` 类就是一个经典的单例，代表着程序的运行时环境；Spring 框架中的应用上下文（`ApplicationContext`）同样被设计为单例，为应用程序中所有 bean 提供一个集中式的访问点。

  ## 题目实战

  ### 题目分析

  理论讲完了，我们回到本篇对应的题目——「小明的购物车」。先把题目读清楚，看看它到底要我们做什么。

  **题目描述**：小明去了一家大型商场，拿到了一个购物车开始购物。我们要设计一个购物车管理器，记录商品被添加进购物车的信息（商品名称和购买数量），并在购物结束后打印出商品清单。题目里特别强调了一句话——**「在整个购物过程中，小明只有一个购物车实例存在」**，这正是本题点名要用单例模式的信号。

  **输入**：包含若干行，每行两部分信息，分别是商品名称和购买数量，中间用空格隔开。例如：

  ```text
  Apple 3
  Banana 2
  Orange 5
  ```

  **输出**：把购物车里所有商品及其购买数量打印出来，每行一种商品，格式为 `商品名称 购买数量`。对应上面的输入，输出为：

  ```text
  Apple 3
  Banana 2
  Orange 5
  ```

  把这道题的考点拎出来看，其实就两件事：

  1. **「只有一个购物车实例」**——这是单例模式的核心约束。无论代码在哪里往车里加东西，操作的都必须是同一个购物车，绝不能各加各的、最后对不上账。
  2. **「按添加顺序打印」**——观察输入输出示例，商品的输出顺序和输入顺序完全一致（Apple、Banana、Orange）。这提醒我们在存储商品时要保留插入顺序，普通的哈希表是无序的，得留个心眼。

  ### 解题思路

  我们一步一步来，先想清楚「如果不用单例会怎样」，再顺势引出正确写法。

  **第一步：识别出我们需要的就是单例。**

  假设我们很随意地写代码，在 main 里 `new` 一个购物车，在某个工具方法里又 `new` 一个购物车：

  ```java
  // 反例：到处 new，造出了好几个购物车
  ShoppingCartManager cartA = new ShoppingCartManager();
  
  cartA.addToCart("Apple", 3);
  
  ShoppingCartManager cartB = new ShoppingCartManager(); // 又造了一个！
  
  cartB.viewCart(); // 这里是空的，Apple 加到 cartA 去了
  ```

  `cartB` 和 `cartA` 是两个完全不同的对象，往 `cartA` 加的商品，`cartB` 自然看不到。这就违背了题目「只有一个购物车实例」的要求。所以我们要做的，是从机制上**杜绝外部随意创建实例**。

  **第二步：把构造函数藏起来，只留一个统一入口。**

  按照前面讲的单例三要素：构造函数私有（不让外面 `new`）、用一个私有静态变量存住唯一实例、再开一个公有静态方法 `getInstance()` 当作领取实例的窗口。

  ```java
  class ShoppingCartManager {
  
      // 私有静态变量，保存唯一实例（饿汉式：类加载时就创建好）
      private static final ShoppingCartManager instance =
          new ShoppingCartManager();
  
      // 私有构造函数，外部无法 new
      private ShoppingCartManager() {}
  
      // 公有静态方法，全局统一入口
      public static ShoppingCartManager getInstance() {
          return instance;
      }
  }
  ```

  这样一来，全程序无论谁调用 `ShoppingCartManager.getInstance()`，拿到的都是同一个购物车。题目这种「程序跑完就结束、不涉及高并发」的场景，用最简单的**饿汉式**就足够稳妥了。

  **第三步：处理「按顺序打印」这个隐藏要求。**

  购物车内部要存「商品名 → 数量」的映射。如果直接用普通哈希表（如 Java 的 `HashMap`），输出顺序就乱了。所以这里选用**能保留插入顺序的结构**——Java 里是 `LinkedHashMap`，C++/Go 里则额外用一个数组记录键的插入次序。同一种商品如果被多次添加，数量要累加。

  **第四步：串起主流程。**

  读取输入直到结束，每读到一行就调用 `getInstance()` 拿到购物车并 `addToCart`，全部读完后调用 `viewCart()` 打印。下面就是落地后的完整代码。

  ### 本题代码

  下面这份参考代码采用了前面讲过的「饿汉模式」来实现，并用 `LinkedHashMap` 保证按添加顺序输出：

  ```java
  import java.util.LinkedHashMap;
  import java.util.Map;
  import java.util.Scanner;
  
  public class Main {
  
      public static void main(String[] args) {
          ShoppingCartManager cart = ShoppingCartManager.getInstance();
          Scanner scanner = new Scanner(System.in);
  
          while (scanner.hasNext()) {
              String itemName = scanner.next();
              int quantity = scanner.nextInt();
  
              // 获取购物车实例并添加商品
              cart.addToCart(itemName, quantity);
          }
  
          // 输出购物车内容
          cart.viewCart();
      }
  }
  
  class ShoppingCartManager {
  
      // 饿汉模式实现单例
      private static final ShoppingCartManager instance =
          new ShoppingCartManager();
  
      // 购物车存储商品和数量的映射
      private Map<String, Integer> cart;
  
      // 私有构造函数
      private ShoppingCartManager() {
          cart = new LinkedHashMap<>();
      }
  
      // 获取购物车实例
      public static ShoppingCartManager getInstance() {
          return instance;
      }
  
      // 添加商品到购物车
      public void addToCart(String itemName, int quantity) {
          cart.put(itemName, cart.getOrDefault(itemName, 0) + quantity);
      }
  
      // 查看购物车
      public void viewCart() {
          for (Map.Entry<String, Integer> entry : cart.entrySet()) {
              System.out.println(entry.getKey() + " " + entry.getValue());
          }
      }
  }
  ```

  ### 其他语言版本

  单例模式的思想是相通的，但不同语言在写法上各有特色。下面收录了几种主流语言的实现，你可以挑选自己熟悉的对照着看。

  #### Java

  这一版采用的是「懒汉 + 双重检查锁」的写法，对照前面的理论部分会更好理解：

  ```java
  import java.util.ArrayList;
  import java.util.Scanner;
  
  class ShoppingCart {
  
      // 购物车类的单例实例变量，使用volatile关键字确保线程安全
      private static volatile ShoppingCart instance;
      // 存储商品名称
      private static ArrayList<String> productNames = new ArrayList<>();
      // 存储商品数量
      private static ArrayList<Integer> productQuantities = new ArrayList<>();
  
      // 私有构造函数，防止外部直接创建ShoppingCart对象
      private ShoppingCart() {}
  
      // 获取购物车单例实例的方法，确保线程安全
      public static ShoppingCart getInstance() {
          if (instance == null) {
              synchronized (ShoppingCart.class) {
                  if (instance == null) {
                      instance = new ShoppingCart();
                  }
              }
          }
          return instance;
      }
  
      // 添加商品到购物车的方法
      public void Add(String name, int quantity) {
          productNames.add(name);
          productQuantities.add(quantity);
          System.out.println(name + " " + quantity);
      }
  }
  
  public class Main {
  
      public static void main(String[] args) {
          ShoppingCart cart = ShoppingCart.getInstance();
          Scanner scanner = new Scanner(System.in);
  
          String inputLine;
          // 循环读取用户输入，直到用户输入"exit"
          while (scanner.hasNextLine()) {
              inputLine = scanner.nextLine();
  
              if ("exit".equalsIgnoreCase(inputLine)) {
                  break;
              }
  
              // 使用空格分割输入的字符串，获取商品名称和数量
              String[] parts = inputLine.split(" ");
  
              // 确保输入格式正确，即包含两个部分：商品名称和数量
              if (parts.length == 2) {
                  // 商品名称
                  String name = parts[0];
                  // 商品数量
                  int quantity;
  
                  try {
                      // 将第二部分转换为整数
                      quantity = Integer.parseInt(parts[1]);
                      cart.Add(name, quantity);
                  } catch (NumberFormatException e) {
                      // 如果转换失败，输出错误信息
                      System.out.println("转换失败，请重新输入");
                  }
              } else {
                  // 如果输入格式不正确，输出错误信息
                  System.out.println("如果输入格式不正确，请重新输入");
              }
          }
  
          scanner.close();
      }
  }
  ```

**你的理解对了一半，但不够全面。** 

准确来说：**`volatile` 的核心作用有两个：① 禁止指令重排序（你提到的）；② 保证内存可见性（你漏掉的）。**

在双重检查锁定（DCL）单例中，这两个作用**缺一不可**。为了让你彻底分清，我拆成两块来讲：

### 1. 禁止指令重排序（你理解的部分）✅

### 1.1 直观层面：指令重排序（核心元凶）

你以为 `instance = new ShoppingCart();` 在 CPU 里是一步完成的吗？**错！** 它底层大致分为 3 个步骤：

1. 在堆内存中开辟一块空间（分配内存）。
2. 调用构造函数，对这块空间进行初始化（填充数据）。
3. 将内存空间的地址赋值给 `instance` 引用（让它指向这块内存）。

**但是**，JVM 和 CPU 为了优化执行效率，可能会**胡乱排序（指令重排序）**。正常情况下顺序是 `1 -> 2 -> 3`，但在某个瞬间，CPU 可能会变成 `1 -> 3 -> 2`！

### 1.2. 不加 `volatile` 的“灵异事件”现场

假设没有 `volatile`，线程 A 和线程 B 同时调用 `getInstance()`：

- **线程 A** 发现 `instance == null`，进入 `synchronized` 块，开始执行 `new ShoppingCart()`。
- 由于指令重排序，CPU 先执行了**第 1 步（分配内存）**和**第 3 步（把地址赋给 `instance`）**，此时 `instance` **已经不为 null** 了（指向了一块内存地址），但**第 2 步（构造函数初始化）还没执行完**（比如 `productNames` 和 `productQuantities` 还是空的或默认值）。
- 就在这个“构造函数刚执行到一半”的瞬间，**线程 B** 也调用了 `getInstance()`。
- 线程 B 一看 `if (instance == null)`，发现 `instance` 已经不是 null 了，于是**直接返回了这个 `instance`**。
- 线程 B 拿着这个还没初始化好的“半成品”购物车，立刻调用 `cart.Add(...)`。

**结果**：因为 `productNames` 还没初始化完成，线程 B 调用 `Add` 时极大概率抛出 **`NullPointerException`（空指针异常）**，程序直接崩溃。

### 1.3. `volatile` 做了什么“魔法”？

加上 `volatile` 后，Java 内存模型会强制加一道**内存屏障（Memory Barrier）**。它的作用是：

> **禁止第 3 步（赋值）跑到第 2 步（构造）前面去。**

这就保证了：**任何其他线程看到 `instance` 指向内存地址的那一刻，这个对象里面的所有数据（构造函数）一定已经执行完毕了**

这是你答对的部分。正如我上个回答所说，`volatile` 通过内存屏障，强行禁止了 `instance = new Singleton()` 这行代码的指令重排，确保对象**先初始化完，再赋值给引用**。这就防止了其他线程拿到一个“半成品”对象。

---

### 2. 保证内存可见性（你漏掉的核心部分）🔥
这是 `volatile` 另一个极其重要的作用。如果没有 `volatile`，即使**没有发生指令重排序**，程序照样可能崩溃！

**“可见性”是什么意思？**
在 Java 内存模型中，每个线程都有自己的 CPU 缓存（工作内存）。线程操作变量时，并不是直接操作主内存，而是先把主内存的数据拷贝到自己的缓存里修改，改完后再刷回主内存。

**不加 `volatile` 的“灵异事件”（仅针对可见性）：**

1. **线程 A** 抢到了锁，执行 `new ShoppingCart()`，在堆里创建好了完整的对象，并把 `instance` 指向了这个对象。**但是**，CPU 为了效率，可能把 `instance` 的最新地址值暂时存放在**线程 A 的 CPU 缓存**中，还没有刷回主内存（RAM）。
2. 此时 **线程 B** 进来了，执行第一个 `if (instance == null)`。
3. 因为线程 B 的 CPU 缓存里没有这个新地址，它只能去**主内存**里读取 `instance`，结果主内存里的 `instance` 依然是 `null`！
4. 线程 B 一看是 `null`，于是也去抢锁，抢到后**又 new 了一个新的对象**，单例彻底被破坏！

**加了 `volatile` 后发生了什么？**
Java 内存模型规定：**只要线程 A 修改了 `volatile` 修饰的变量，JVM 会强制要求线程 A 立刻把最新值刷回主内存，并且强制让线程 B 缓存里的 `instance` 失效，迫使线程 B 必须去主内存重新读取。**

这样，线程 A 刚赋完值，线程 B 立马就能看到最新的 `instance`，这就是“可见性”的保障。

| **禁止指令重排序** | 保证写操作在赋值前，所有构造函数都执行完       | 防止拿到半成品（未初始化的对象）               |
| **保证内存可见性** | 强制修改后立即刷新主内存，并让其他线程缓存失效 | 防止其他线程看到过期的 `null` 值，导致重复创建 |

---

### 特别提醒（避免误区）

> **`volatile` 不能保证原子性！**
> 比如 `count++` 这种操作，即使加了 `volatile` 也不安全，因为读-改-写三步不是原子的，需要用 `synchronized` 或 `Atomic` 类。
>
> **但在你的代码中**，`instance = new ShoppingCart()` 这一行，赋值操作（把地址给 `instance`）本身就是**原子性的**，所以结合 `volatile` 的可见性和禁止重排序，就完美无缺了。

**一句话帮你记牢：**
> `volatile` = **不重排**（有序性）+ **及时看**（可见性）。在单例 DCL 中，它俩联手，确保了单例既不会被半成品坑，也不会被旧缓存坑。



## 2. 装饰模式

## 模式详解

### 基本概念

通常情况下，扩展类的功能可以通过继承实现，但是扩展越多，子类越多，装饰模式（`Decorator Pattern`, 结构型设计模式）可以在**不定义子类的情况下动态的给对象添加一些额外的功能。**具体的做法是将原始对象放入包含行为的特殊封装类（装饰类），从而为原始对象动态添加新的行为，而无需修改其代码。

用一个生活化的类比来感受一下：你去咖啡店点了一杯黑咖啡，这是基础款。然后服务员问你「要加牛奶吗？」「要加糖吗？」你选了加糖——服务员不会去重新煮一杯新的咖啡，而是直接把糖加到你的杯子里。这个「加糖」的动作，就是对咖啡对象的一次**装饰**：原来的咖啡还在，只是被额外的行为包裹了一层。

再比如，假设你有一个基础的图形类，你想为它添加颜色、边框、阴影等功能。如果每个功能都实现一个子类——「带颜色的图形」「带边框的图形」「带颜色又带边框的图形」——就会产生大量的类，而且每种组合都要单独写代码。装饰模式的思路则截然不同：它允许你像套娃一样，把一个对象包进一个「装饰类」，装饰类再包进另一个装饰类，每层包裹都叠加一种新行为，而核心对象本身纹丝不动。

### 基本结构

装饰模式包含以下四个主要角色：

![装饰模式结构图](https://file1.kamacoder.com/i/web/20260612161928-16472.png)

- 组件 `Component`：通常是抽象类或者接口，是具体组件和装饰者的父类，定义了具体组件需要实现的方法。比如说我们定义 `Coffee` 为组件接口，规定所有咖啡都要实现 `brew()` 方法。
- 具体组件 `ConcreteComponent`：实现了 Component 接口的具体类，是**被装饰的对象**。比如「黑咖啡」`BlackCoffee`、「拿铁」`Latte`，它们是真正的咖啡本体。
- 装饰类 `Decorator`：一个抽象类，**同样实现 Component 接口**，持有一个指向 Component 对象的引用。它本身不添加新功能，只是把调用转发给被包裹的对象——但这个设计让所有具体装饰类都能无缝替换原始对象。
- 具体装饰类 `ConcreteDecorator`：扩展 Decorator 类，负责向 Component 对象添加新的行为。「加牛奶的咖啡」是一个具体装饰类，「加糖的咖啡」也是一个具体装饰类。

装饰模式的精髓在于：**装饰类和具体组件都实现同一个接口**，这让客户端完全无感知——无论是原始的黑咖啡，还是套了两层装饰的「加糖加奶黑咖啡」，对外的样子都是一个 `Coffee`，都能调用 `brew()`。

### 基本实现

装饰模式的实现包括以下步骤：

1. 定义 Component 接口

```java
// 组件接口
public interface Component {
    void operation();
}
```

1. 实现 ConcreteComponent

```java
// 具体组件
public class ConcreteComponent implements Component {
    @Override
    public void operation() {
        System.out.println("ConcreteComponent operation");
    }
}
```

1. 定义 Decorator 装饰类，继承自 Component

```java
// 定义一个抽象的装饰者类，继承自Component
public abstract class Decorator implements Component {
    protected Component component;

    public Decorator(Component component) {
        this.component = component;
    }

    @Override
    public void operation() {
        component.operation();
    }
}
```

1. 定义具体的装饰者实现，给具体组件对象添加功能。

```java
// 具体的装饰者实现
public class ConcreteDecorator extends Decorator {

    public ConcreteDecorator(Component component) {
        super(component);
    }

    // 根据需要添加额外的方法

    @Override
    public void operation() {
        // 可以在调用前后添加额外的行为
        System.out.println("Before operation in ConcreteDecorator");
        super.operation();
        System.out.println("After operation in ConcreteDecorator");
    }
}
```

1. 在客户端使用

```java
public class Main {

    public static void main(String[] args) {
        // 创建具体组件
        Component concreteComponent = new ConcreteComponent();

        // 使用具体装饰者包装具体组件
        Decorator decorator = new ConcreteDecorator(concreteComponent);

        // 调用操作
        decorator.operation();
    }
}
```

注意客户端的写法：`new ConcreteDecorator(concreteComponent)`——装饰者把被装饰对象作为构造函数参数传入，之后对外完全以 `Component` 的面目示人。如果还想再叠一层，只需再套一个 `new AnotherDecorator(decorator)`，就像俄罗斯套娃，层数完全由你控制。

### 应用场景

装饰模式通常在以下几种情况使用：

- 当需要给一个现有类添加附加功能，但由于某些原因不能使用继承来生成子类进行扩充时，可以使用装饰模式。
- 动态的添加和覆盖功能：当对象的功能要求可以动态地添加，也可以再动态地撤销时可以使用装饰模式。

在 Java 的 I/O 库中，装饰者模式被广泛用于增强 I/O 流的功能。例如，`BufferedInputStream` 和 `BufferedOutputStream` 这两个类提供了缓冲区的支持，通过在底层的输入流和输出流上添加缓冲区，提高了读写的效率，它们都是 `InputStream` 和 `OutputStream` 的装饰器。`BufferedReader` 和 `BufferedWriter` 这两个类与 `BufferedInputStream` 和 `BufferedOutputStream` 类似，提供了字符流的缓冲功能，是 Reader 和 Writer 的装饰者。

## 题目实战

### 题目分析

题目背景是：小明喜欢品尝不同口味的咖啡，他发现每种咖啡都可以加入不同的调料。系统支持两种咖啡类型：**黑咖啡（Black Coffee）** 和 **拿铁（Latte）**，以及两种调料：**牛奶（Milk）** 和 **糖（Sugar）**。

**输入格式**：多行输入，每行包含两个数字。第一个数字表示咖啡类型（1 表示黑咖啡，2 表示拿铁），第二个数字表示调料类型（1 表示牛奶，2 表示糖）。

**输出格式**：根据每行输入，输出制作咖啡的过程，包括咖啡类型和添加的调料。

来看示例：

输入：

```text
1 1
2 2
```

输出：

```text
Brewing Black Coffee
Adding Milk
Brewing Latte
Adding Sugar
```

观察输出可以发现：**每次输出两行**——先输出咖啡本身的制作信息，再输出添加调料的信息。这两步顺序固定，且是在同一次 `brew()` 调用中连续打印的。

题目考点非常清晰：两种咖啡是**具体组件**，两种调料是**具体装饰类**，装饰模式的「套娃」结构让调料的添加过程自然地叠加在咖啡制作过程之后。

### 解题思路

我们一步步把这道题的设计推导出来。

**第一步：识别「被装饰的对象」。** 题目里有两种咖啡：黑咖啡和拿铁。它们是核心对象，代表「咖啡本体」。这里先定义一个 `Coffee` 接口，规定所有咖啡都要实现 `brew()` 方法：

```java
// 示意：定义统一接口
interface Coffee {
    void brew();
}
// 黑咖啡和拿铁分别实现这个接口
class BlackCoffee implements Coffee { ... }
class Latte implements Coffee { ... }
```

**第二步：识别「装饰行为」。** 调料（牛奶、糖）是「附加行为」，它们不是独立的咖啡类型，而是对已有咖啡对象的包装。我们定义一个抽象 `Decorator` 类，它同样实现 `Coffee` 接口，并持有一个 `Coffee` 实例：

```java
// 示意：装饰者也实现 Coffee 接口
abstract class Decorator implements Coffee {
    protected Coffee coffee;
    public Decorator(Coffee coffee) { this.coffee = coffee; }

    @Override
    public void brew() {
        coffee.brew();  // 先把调用转发给被装饰的咖啡
    }
}
```

关键在于：`Decorator` 的 `brew()` 先调用了内部 `coffee.brew()`，相当于「先出咖啡，再加配料」。具体装饰类只需在 `super.brew()` 之后追加自己的输出即可。

**第三步：实现具体装饰类。** 每种调料对应一个具体装饰类，复写 `brew()` 方法，先调用 `super.brew()` 触发咖啡的制作，再追加自己的输出：

```java
// 示意：具体装饰类的套路
class MilkDecorator extends Decorator {
    public MilkDecorator(Coffee coffee) { super(coffee); }

    @Override
    public void brew() {
        super.brew();               // → Brewing Black Coffee
        System.out.println("Adding Milk");  // → Adding Milk
    }
}
```

这样，当客户端调用 `milkCoffee.brew()` 时，执行顺序是：`MilkDecorator.brew()` → `super.brew()` → `BlackCoffee.brew()` 打印 `Brewing Black Coffee` → 返回 → 打印 `Adding Milk`。两行输出自然产生，顺序也完全符合题目要求。

**第四步：在客户端组装并循环调度。** 每行输入包含两个数字，先根据第一个数字创建咖啡对象，再根据第二个数字用对应装饰类包裹它，最后调用 `brew()`：

```java
// 示意：客户端的组装过程
Coffee coffee = new BlackCoffee();       // 第一层：咖啡本体
coffee = new MilkDecorator(coffee);      // 第二层：用装饰类包裹
coffee.brew();                           // 调用一次，两行输出
```

整体设计简洁：一个接口、两个具体组件、一个抽象装饰类、两个具体装饰类，加上循环读取输入的 `main` 方法。

### 本题代码

```java
import java.util.Scanner;

// 咖啡接口
interface Coffee {
    void brew();
}

// 具体的黑咖啡类
class BlackCoffee implements Coffee {

    @Override
    public void brew() {
        System.out.println("Brewing Black Coffee");
    }
}

// 具体的拿铁类
class Latte implements Coffee {

    @Override
    public void brew() {
        System.out.println("Brewing Latte");
    }
}

// 装饰者抽象类
abstract class Decorator implements Coffee {

    protected Coffee coffee;

    public Decorator(Coffee coffee) {
        this.coffee = coffee;
    }

    @Override
    public void brew() {
        coffee.brew();
    }
}

// 具体的牛奶装饰者类
class MilkDecorator extends Decorator {

    public MilkDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public void brew() {
        super.brew();
        System.out.println("Adding Milk");
    }
}

// 具体的糖装饰者类
class SugarDecorator extends Decorator {

    public SugarDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public void brew() {
        super.brew();
        System.out.println("Adding Sugar");
    }
}

// 客户端代码
public class Main {

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);

        while (scanner.hasNext()) {
            int coffeeType = scanner.nextInt();
            int condimentType = scanner.nextInt();

            // 根据输入制作咖啡
            Coffee coffee;
            if (coffeeType == 1) {
                coffee = new BlackCoffee();
            } else if (coffeeType == 2) {
                coffee = new Latte();
            } else {
                System.out.println("Invalid coffee type");
                continue;
            }

            // 根据输入添加调料
            if (condimentType == 1) {
                coffee = new MilkDecorator(coffee);
            } else if (condimentType == 2) {
                coffee = new SugarDecorator(coffee);
            } else {
                System.out.println("Invalid condiment type");
                continue;
            }

            // 输出制作过程
            coffee.brew();
        }
    }
}
```
